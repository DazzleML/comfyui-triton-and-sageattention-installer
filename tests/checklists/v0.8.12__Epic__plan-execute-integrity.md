# Human Test Checklist: Plan/Execute Integrity Release

**Target version:** v0.8.12
**Ships with commit:** TBD (pre-commit at time of writing; folds in the untagged v0.8.11 setuptools fix)
**Companion automated tests:** 215 tests in `tests/unit/` — `test_installplan_matrix.py` (87), `test_installation_target.py` (32), `test_setuptools_constraint.py` (24), `test_backup.py` (21), `test_plan_exec_agreement.py` (20), `test_confirm_prompt.py` (19), `test_display_rendering.py` (8), `test_sa_downgrade_packaging_fallback.py` (4)

## What this is

v0.8.12 fixes a fresh install failing outright on CUDA 13.2, plus a group of defects that let `--dryrun` predict one thing while the real run did another. Both classes are invisible to the existing test matrix: it verifies that a *plan* is generated correctly against a fully-populated environment, and never runs an installation path. Every defect below was found by running the installer against real environments, not by a test.

This checklist is what a person should run to verify the release end-to-end. It is written so an external tester with a Windows machine, an NVIDIA GPU, and a ComfyUI install can execute it without access to any project-internal document.

**The property under test throughout:** *the preview must never make a claim the install contradicts.* Wherever a step asks you to compare `--dryrun` output against a real run, that comparison is the point of the test.

## Legend — defect codes used in this document

Codes appear in section headings so maintainers can trace a test back to the defect it guards. Testers do not need them; each test states its own expected behavior.

| Code | Defect |
|---|---|
| D1 | `--sage-version` never reached the plan; preview said "Nothing to do" while the run downgraded SageAttention |
| D2 | Fresh install: plan computed the SageAttention target against the not-yet-installed PyTorch |
| D3 | Plain `--install` ignored a KEEP decision and reinstalled SageAttention anyway |
| D4 | `packaging` imported outside its guard — `ImportError` instead of the fallback path |
| D5 | `--force` was honored for PyTorch only; Triton and SageAttention silently stayed at KEEP |
| D6 | The "newer than we know about" shortcut fired before an explicit `--sage-version` was read |
| D7 | The plan resolved CUDA from PyTorch first; execution re-probed `nvcc` and could disagree |
| D8 | Triton's planned target was unconstrained while execution pinned a version range |
| D9 | ~96 lines of downgrade-detection helpers that shipped with no callers |
| D10 | Wheel matching read the Python running the installer, not the target environment's |
| CU132 | The `cu132` PyTorch index has no `torchaudio`, so a fresh CUDA 13.2 install failed entirely |

## Prerequisites

1. **Windows** with an NVIDIA GPU and a working driver. Some sections need CUDA 13.2 specifically — they are marked and skippable.
2. **Python 3.10–3.13** on PATH. Section 6 additionally needs *two different* Python versions installed.
3. **Internet access.** A full fresh install downloads ~3 GB of PyTorch wheels.
4. **Disk:** ~8 GB free for the scratch ComfyUI used in Sections 1 and 2.
5. **Never run this checklist against your real ComfyUI** except where a section explicitly says to, and only after taking the backup in Section 7.

### State isolation

Every section uses a scratch ComfyUI directory. Set it once per shell:

**cmd.exe**:
```cmd
set CTS_SCRATCH=%TEMP%\cts_checklist
set CTS_REPO=C:\code\comfyui-triton-sageattention-installer\local
mkdir "%CTS_SCRATCH%"
```

**PowerShell**:
```powershell
$env:CTS_SCRATCH = "$env:TEMP\cts_checklist"
$env:CTS_REPO = "C:\code\comfyui-triton-sageattention-installer\local"
New-Item -ItemType Directory -Force $env:CTS_SCRATCH | Out-Null
```

**POSIX (Git Bash / WSL)**:
```bash
export CTS_SCRATCH="$TEMP/cts_checklist"
export CTS_REPO="/c/code/comfyui-triton-sageattention-installer/local"
mkdir -p "$CTS_SCRATCH"
```

### Reset between sections

To return to a clean fresh-install state (no PyTorch), delete and recreate the venv. This is fast; the expensive part is re-downloading PyTorch, so only do it when a section asks.

**cmd.exe**:
```cmd
rmdir /s /q "%CTS_SCRATCH%\ComfyUI\venv"
python -m venv "%CTS_SCRATCH%\ComfyUI\venv"
```

**PowerShell**:
```powershell
Remove-Item -Recurse -Force "$env:CTS_SCRATCH\ComfyUI\venv"
python -m venv "$env:CTS_SCRATCH\ComfyUI\venv"
```

**POSIX**:
```bash
rm -rf "$CTS_SCRATCH/ComfyUI/venv"
python -m venv "$CTS_SCRATCH/ComfyUI/venv"
```

## High-Value Verification (~10 minutes, plus one ~15 minute download)

**If you only have time for six tests, run these.** If any fails, the release is broken and the detailed sections below will not rescue it.

### HV.1 — A fresh install completes on CUDA 13.2 (CU132)

Validates the release-blocking fix. Before v0.8.12, this failed outright and installed nothing.

> Skip if your machine is not on CUDA 13.2. Check with `nvcc --version`. On any other CUDA version this test still passes but proves less.

- [ ] **Steps:**
  1. Create a fresh ComfyUI and empty venv:

     **cmd.exe**:
     ```cmd
     git clone --depth 1 https://github.com/comfyanonymous/ComfyUI.git "%CTS_SCRATCH%\ComfyUI"
     python -m venv "%CTS_SCRATCH%\ComfyUI\venv"
     ```

     **PowerShell**:
     ```powershell
     git clone --depth 1 https://github.com/comfyanonymous/ComfyUI.git "$env:CTS_SCRATCH\ComfyUI"
     python -m venv "$env:CTS_SCRATCH\ComfyUI\venv"
     ```

     **POSIX**:
     ```bash
     git clone --depth 1 https://github.com/comfyanonymous/ComfyUI.git "$CTS_SCRATCH/ComfyUI"
     python -m venv "$CTS_SCRATCH/ComfyUI/venv"
     ```
  2. Run the install (takes ~15 min, downloads ~3 GB):
     ```
     python comfyui_triton_sageattention.py --install --non-interactive --base-path "<CTS_SCRATCH>/ComfyUI"
     ```
- [ ] **Expected:** Exit code 0, and PyTorch, torchvision, **torchaudio**, Triton and SageAttention all present afterward.
- [ ] **Check:** `<venv>\Scripts\python.exe -m pip list` shows all five. `pip check` reports `No broken requirements found`.
- [ ] **Must NOT see:** `ERROR: No matching distribution found for torchaudio`, or a run that prints `Success!` while having installed nothing.
- [ ] **Why this matters:** On CUDA 13.2 the installer previously asked pip for torch + torchvision + torchaudio from the `cu132` index, which publishes no torchaudio at all. pip failed the whole transaction, so a brand-new user could not install anything.

### HV.2 — The preview does not promise a version it cannot know (D2/D8)

Validates the core invariant on the fresh-install path.

- [ ] **Steps:** Reset the venv (see Reset above), then:
  ```
  python comfyui_triton_sageattention.py --install --dryrun --non-interactive --base-path "<CTS_SCRATCH>/ComfyUI"
  ```
- [ ] **Expected:** The SageAttention line reads `determined after PyTorch installs`. The Wheel Details section says the wheel is selected after PyTorch installs. Every CUDA number shown for PyTorch and for the wheel agrees.
- [ ] **Must NOT see:** `Will install: SA 1.0.6 from PyPI`, or a warning that no SA 2.x wheel exists, or a specific wheel URL.
- [ ] **Why this matters:** PyTorch installs *before* SageAttention, so any wheel the preview names here was computed against a PyTorch that is not there yet. The real run then installs something else — which is exactly the class of lie this release exists to remove.

### HV.3 — `--sage-version` is honored by the preview (D1)

The most user-harming defect: the preview said nothing would happen, then the real run downgraded a working install.

> Needs an environment that already has SageAttention 2.x. Use the one HV.1 produced.

- [ ] **Steps:**
  ```
  python comfyui_triton_sageattention.py --install --dryrun --non-interactive --sage-version 1 --base-path "<CTS_SCRATCH>/ComfyUI"
  ```
- [ ] **Expected:** SageAttention shows `[DOWNGRADE]` from your installed 2.x to `1.0.6`, and a backup recommendation appears.
- [ ] **Must NOT see:** `Nothing to do - all components are already up to date`.
- [ ] **Why this matters:** Before this fix, that exact command printed "Nothing to do" and the identical command without `--dryrun` uninstalled SageAttention 2.2.0.post6 and installed 1.0.6.

### HV.4 — Plain `--install` does nothing to a healthy environment (D3)

- [ ] **Steps:** Against the environment HV.1 produced:
  ```
  python comfyui_triton_sageattention.py --install --non-interactive --base-path "<CTS_SCRATCH>/ComfyUI"
  ```
- [ ] **Expected:** All three components report `KEEP`. No `pip install` of torch, triton or sageattention runs. Finishes in seconds, not minutes.
- [ ] **Check:** Note the SageAttention version before and after — it must be byte-identical, including the `+cu...post...` local part.
- [ ] **Why this matters:** Previously the plan said KEEP and execution ignored it, uninstalling and reinstalling the same SageAttention version on every run.

### HV.5 — `--force` reaches all three components (D5)

- [ ] **Steps:**
  ```
  python comfyui_triton_sageattention.py --install --force --dryrun --non-interactive --base-path "<CTS_SCRATCH>/ComfyUI"
  ```
- [ ] **Expected:** All three of PyTorch, Triton and SageAttention show `REINSTALL` (not `KEEP`).
- [ ] **Why this matters:** `--force` was honored for PyTorch only. For Triton and SageAttention it was a silent no-op — the flag appeared to work and did nothing.

### HV.6 — The kernel actually works (not just installs)

Installation succeeding is not the same as the GPU math being right. This matters especially on CUDA 13.2, where the installer now deliberately uses CUDA 13.0 builds.

- [ ] **Steps:**
  ```
  <venv>\Scripts\python.exe tests/one-offs/_cuda129_inner_kernel_test.py
  ```
- [ ] **Expected:** `RESULT: PASS kernel_correct`, with a reported cosine similarity above 0.99 (expect ~0.99933).
- [ ] **Must NOT see:** `FAIL cuda_not_available`, `FAIL import_sageattention`, `FAIL kernel_inaccurate`, or a non-finite output.
- [ ] **Why this matters:** The CUDA 13.2 fix substitutes cu130 builds on a 13.2 driver. That substitution is only legitimate if the resulting attention kernel produces correct numbers, so this is the test that licenses the fix.

## Section 1: Fresh-install path (~20 min, mostly download)

The single least-covered path in the automated suite — no test environment has ever lacked PyTorch.

### 1.1 Preview and run agree on a fresh install

- [ ] **Steps:**
  1. Reset the venv.
  2. Capture the preview to a file:

     **cmd.exe**: `python comfyui_triton_sageattention.py --install --dryrun --non-interactive --base-path "%CTS_SCRATCH%\ComfyUI" > "%TEMP%\preview.txt"`

     **PowerShell**: `python comfyui_triton_sageattention.py --install --dryrun --non-interactive --base-path "$env:CTS_SCRATCH\ComfyUI" | Out-File "$env:TEMP\preview.txt"`

     **POSIX**: `python comfyui_triton_sageattention.py --install --dryrun --non-interactive --base-path "$CTS_SCRATCH/ComfyUI" > "$TEMP/preview.txt"`
  3. Run the real install.
  4. Compare what was installed against what the preview said.
- [ ] **Expected:** Nothing the preview asserted is contradicted. Where the preview declined to name a version, any outcome is acceptable.
- [ ] **Check:** The PyTorch CUDA in the preview matches `torch.version.cuda` afterward:
  ```
  <venv>\Scripts\python.exe -c "import torch; print(torch.__version__, torch.version.cuda)"
  ```

### 1.2 A machine with no CUDA toolkit still previews sanely

- [ ] **Steps:** On a machine (or PATH) without `nvcc`, run `--install --dryrun`.
- [ ] **Expected:** CPU backend is reported clearly. No traceback. The preview does not claim a CUDA wheel.
- [ ] **Note:** Temporarily removing CUDA from PATH is enough; you do not need to uninstall anything.

### 1.3 Error output during a fresh install is not alarming

- [ ] **Steps:** Watch the console during a fresh `--install`.
- [ ] **Expected:** Probes for packages that are legitimately absent should not look like failures.
- [ ] **Known issue (pre-existing, not a regression):** Four `ERROR - Command failed` lines with `importlib.metadata.PackageNotFoundError` tracebacks appear while checking whether Triton and SageAttention are installed. They are harmless — the installer is asking "is this present?" and the answer is "no" — but they read as crashes to a new user. Confirm they are *only* these probes and that the install proceeds normally. Note anything else that looks like an error.

## Section 2: Preview/run agreement on a populated environment (~10 min)

### 2.1 The `--sage-version` matrix (D1, D6)

Run each against an environment with SageAttention 2.x installed and confirm the preview matches what a real run would do.

| Request | Expected action | Expected Wheel Details |
|---|---|---|
| `auto` | `KEEP` | the installed wheel's URL |
| `1` | `DOWNGRADE` to 1.0.6 | "SA 1.x requested — installing 1.0.6 from PyPI" |
| `2` | `KEEP` | the installed wheel's URL |
| `2.1.1` | `DOWNGRADE` to 2.1.1 | "SA 2.1.1 requested — availability resolved during install" |

- [ ] **Steps:** For each row:
  ```
  python comfyui_triton_sageattention.py --install --dryrun --non-interactive --sage-version <REQUEST> --base-path "<CTS_SCRATCH>/ComfyUI"
  ```
- [ ] **Expected:** The table above, exactly. The four requests must not produce identical output.
- [ ] **Check specifically:** For `--sage-version 1`, there must be **no** warning saying no SA 2.x wheel exists for your environment — one does exist; you declined it. That wording was wrong before this release.
- [ ] **Check specifically:** For `--sage-version 2.1.1`, the Wheel Details must not show the URL of the wheel you already have installed.

### 2.2 Downgrade consent is requested (D1)

- [ ] **Steps:** Run the `--sage-version 1` case **interactively** (omit `--non-interactive`), and answer `n` at the prompt.
- [ ] **Expected:** A backup recommendation and an explicit confirmation prompt appear before anything is modified. Answering `n` leaves the environment untouched.
- [ ] **Check:** Confirm your SageAttention version is unchanged afterward.
- [ ] **This is interactive** — automated tests cannot verify the prompt renders correctly or that Ctrl-C is safe. Try Ctrl-C too.

### 2.3 A SageAttention version newer than the installer knows is left alone (D6)

- [ ] **Steps:** If you have (or can fake) a SageAttention 3.x install, run a plain `--install --dryrun` with no `--sage-version`.
- [ ] **Expected:** `KEEP`, with a reason noting the version is newer than the installer knows about.
- [ ] **Then:** Run again *with* `--sage-version 2`.
- [ ] **Expected:** Now it plans the change rather than silently claiming KEEP — an explicit request must not be ignored.

## Section 3: CUDA resolution (~5 min, no downloads)

### 3.1 An existing PyTorch's CUDA wins over `nvcc` (D7)

This is the historically dangerous one — see issue #18, where a stale system toolkit caused a working install to be downgraded.

- [ ] **Steps:** On a machine where `nvcc --version` reports a *different* CUDA than `torch.version.cuda` (common with ComfyUI Portable, which bundles its own CUDA), run:
  ```
  python comfyui_triton_sageattention.py --install --dryrun --base-path "<your ComfyUI>"
  ```
- [ ] **Expected:** The CUDA shown is PyTorch's, not `nvcc`'s. PyTorch shows `KEEP`.
- [ ] **Must NOT see:** Any proposal to reinstall PyTorch at the `nvcc`-reported CUDA version.
- [ ] **Why this matters:** In v0.6.8 this exact situation downgraded a working PyTorch 2.9.1+cu130 to 2.7.0+cu126 and took Triton and SageAttention with it.

### 3.2 `--force` with a missing `nvcc` does not install CPU-only PyTorch (D7)

- [ ] **Steps:** With CUDA removed from PATH but a working CUDA PyTorch installed, run `--install --force --dryrun`.
- [ ] **Expected:** The reinstall targets PyTorch's own CUDA version.
- [ ] **Must NOT see:** A CPU-only PyTorch target. That would replace a working GPU install with a CPU one.

### 3.3 CUDA 13.2 routes to the cu130 index (CU132)

- [ ] **Steps:** On a CUDA 13.2 machine with no PyTorch installed, run `--install --dryrun`.
- [ ] **Expected:** The environment reports CUDA 13.2, and the PyTorch line targets **CUDA 13.0**, with a reason explaining the 13.2 wheels are incomplete upstream.
- [ ] **Check:** The Wheel Details CUDA agrees with the PyTorch line — the preview must not show 13.2 in one place and 13.0 in another.
- [ ] **Check:** CUDA 12.9 machines are **not** redirected. If you have one, confirm the PyTorch line still says 12.9. (The SageAttention *wheel* for 12.9 does come from the cu128 build — that is a separate and intended alias.)

## Section 4: Robustness and regressions (~5 min)

### 4.1 No crash when `packaging` is unavailable (D4)

- [ ] **Steps:** In a venv without the `packaging` library, run `--show-installed` and `--install --dryrun`.

  **cmd.exe**: `<venv>\Scripts\python.exe -m pip uninstall -y packaging`

  **PowerShell / POSIX**: same command, adjusting the path separator.
- [ ] **Expected:** Both commands complete. No `ImportError`, no traceback.
- [ ] **Restore:** `<venv>\Scripts\python.exe -m pip install packaging`

### 4.2 Non-install entry points do not crash (regression guard)

The plan is only built by `--install`/`--upgrade`. Everything else must still work.

- [ ] **Steps:** Run each of:
  ```
  python comfyui_triton_sageattention.py --version
  python comfyui_triton_sageattention.py --help
  python comfyui_triton_sageattention.py --show-installed --base-path "<CTS_SCRATCH>/ComfyUI"
  python comfyui_triton_sageattention.py --show-installed locations
  ```
- [ ] **Expected:** All succeed. `--version` reports `0.8.12`.
- [ ] **Must NOT see:** `AttributeError` mentioning `_current_plan`.

### 4.3 Discovery still works

- [ ] **Steps:** `python comfyui_triton_sageattention.py --show-installed discover`
- [ ] **Expected:** Your real ComfyUI installations are listed, including any ComfyUI Desktop install (which has no `main.py`). Selection is presented clearly.
- [ ] **Then:** Ctrl-C out of the selection prompt. It should exit cleanly, with no traceback.
- [ ] **Note:** a genuine Windows Ctrl-C cannot be sent reliably from an automated harness, so this step is human-only. Closing stdin (EOF) is a different code path and is not a substitute.

### 4.4 `--show-installed` reporting

- [ ] **Steps:** Run `--show-installed` against a populated environment.
- [ ] **Expected:** Versions match what `pip list` reports. Table columns align in your terminal.
- [ ] **Known cosmetic issue (pre-existing):** With no PyTorch installed, the CUDA row can report `12.8` regardless of your actual toolkit — an internal default surfacing in the report. It does not affect what gets installed (compare with `--install --dryrun`, which reports correctly). Note it if you see it; do not treat it as a new regression.

## Section 5: The setuptools constraint fix (from the untagged 0.8.11) (~5 min)

### 5.1 A declared upper bound is respected

- [ ] **Steps:** In an environment with PyTorch 2.12.x (which declares `setuptools<82`), run `--install`.
- [ ] **Expected:** The output includes `Respecting installed constraint: setuptools<82`.
- [ ] **Check:** `<venv>\Scripts\python.exe -m pip check` reports `No broken requirements found`.
- [ ] **Check:** setuptools is below 82.

### 5.2 An already-broken environment is repaired

- [ ] **Steps:** Deliberately break it, then re-run:
  ```
  <venv>\Scripts\python.exe -m pip install --upgrade "setuptools>=83"
  <venv>\Scripts\python.exe -m pip check
  python comfyui_triton_sageattention.py --install --non-interactive --base-path "<...>"
  <venv>\Scripts\python.exe -m pip check
  ```
- [ ] **Expected:** `pip check` goes from reporting a conflict to `No broken requirements found`.

### 5.3 An unconstrained environment is unaffected

- [ ] **Steps:** In an environment with PyTorch 2.13 (no setuptools ceiling), run `--install`.
- [ ] **Expected:** setuptools upgrades normally. torch 2.13 declares `setuptools>=77.0.3`, a permissive lower bound, so a constraint line *is* printed — it simply does not restrict the upgrade. What must NOT appear is an upper bound.

## Section 6: Cross-Python behavior (D10) (~10 min)

**Requires two Python versions installed** (for example 3.12 and 3.13). This is the defect where the installer read the wrong interpreter.

### 6.1 The target environment's Python is used, not the launcher's

- [ ] **Steps:** Create a venv with your **older** Python, then run the installer with your **newer** one:

  **cmd.exe**:
  ```cmd
  py -3.12 -m venv "%CTS_SCRATCH%\py312venv"
  py -3.13 comfyui_triton_sageattention.py --show-installed --base-path "%CTS_SCRATCH%\ComfyUI" --python "%CTS_SCRATCH%\py312venv\Scripts\python.exe"
  ```

  **PowerShell**:
  ```powershell
  py -3.12 -m venv "$env:CTS_SCRATCH\py312venv"
  py -3.13 comfyui_triton_sageattention.py --show-installed --base-path "$env:CTS_SCRATCH\ComfyUI" --python "$env:CTS_SCRATCH\py312venv\Scripts\python.exe"
  ```

  **POSIX**:
  ```bash
  py -3.12 -m venv "$CTS_SCRATCH/py312venv"
  py -3.13 comfyui_triton_sageattention.py --show-installed --base-path "$CTS_SCRATCH/ComfyUI" --python "$CTS_SCRATCH/py312venv/Scripts/python.exe"
  ```
- [ ] **Expected:** The reported Python version is **3.12** (the target), not 3.13 (the launcher).
- [ ] **Why this matters:** Typing `py comfyui_triton_sageattention.py` selects your newest installed Python, which is frequently not the one ComfyUI uses.

### 6.2 An exact wheel request matches the target's Python

- [ ] **Steps:** Using the mismatched setup above, request an exact version that has per-Python wheels:
  ```
  py -3.13 comfyui_triton_sageattention.py --install --dryrun --non-interactive --sage-version 2.1.1 --base-path "<...>" --python "<3.12 venv python>"
  ```
- [ ] **Expected:** Any wheel filename shown carries the target's Python tag (`cp312`), never the launcher's (`cp313`).
- [ ] **Also test the `packaging` fallback.** Deciding whether a request lowers the installed version needs the optional `packaging` library, and it is resolved by the *launching* interpreter. Uninstall it from one of your Pythons (`py -3.13 -m pip uninstall -y packaging`) and repeat the command above against an environment holding SageAttention 2.2.x:
  ```
  py -3.13 comfyui_triton_sageattention.py --install --dryrun --non-interactive --sage-version 2.1.1 --python "<venv with SA 2.2.x>"
  py -3.12 comfyui_triton_sageattention.py --install --dryrun --non-interactive --sage-version 2.1.1 --python "<same venv>"
  ```
  Both must report `DOWNGRADE` to 2.1.1. If the `packaging`-less one says `Nothing to do`, the request is being silently dropped — a same-major-version request (2.2.0 → 2.1.1) is exactly the case a major-number-only comparison misses.
- [ ] **Note:** The default `auto` path is unaffected by this defect — it selects ABI3 wheels that cover Python 3.10+, so both interpreters resolve identically. Only exact requests and Pythons below a wheel's floor were affected.

## Section 7: Your real environment (~10 min) — DO THIS LAST

Only after every section above passes. This touches an installation you care about.

### 7.1 Back up first

- [ ] **Steps:**
  ```
  python comfyui_triton_sageattention.py --backup --base-path "<your real ComfyUI>"
  ```
- [ ] **Expected:** A backup is created and its location reported.
- [ ] **Check:** Confirm the backup exists on disk before continuing. Verify `--backup list` shows it.

### 7.2 Preview before acting

- [ ] **Steps:**
  ```
  python comfyui_triton_sageattention.py --show-installed --base-path "<your real ComfyUI>"
  python comfyui_triton_sageattention.py --install --dryrun --base-path "<your real ComfyUI>"
  python comfyui_triton_sageattention.py --upgrade --dryrun --base-path "<your real ComfyUI>"
  ```
- [ ] **Expected:** On a healthy, current environment `--install --dryrun` shows all three as `KEEP`. `--upgrade --dryrun` may legitimately propose newer Triton or SageAttention — read it before agreeing.
- [ ] **Decide deliberately:** An upgrade offer is not an instruction. If your setup works and the offer is only a minor version bump, declining is a valid outcome.

### 7.3 The no-op install (the real test of D3)

- [ ] **Steps:**
  ```
  python comfyui_triton_sageattention.py --install --base-path "<your real ComfyUI>"
  ```
- [ ] **Expected:** All three `KEEP`. Completes in seconds. No package is uninstalled or reinstalled.
- [ ] **Check:** Record exact versions before and after — they must be identical, including local version parts.

## What the automated tests DON'T cover

- **Real pip resolution.** The suite mocks subprocesses. It cannot know that the `cu132` index has no torchaudio — that defect was found by running an install, and no test would have caught it.
- **Whether an installed package actually works.** Tests verify what the installer *decided*, not that the resulting GPU kernel computes correct values. HV.6 is the only check of that.
- **Interactive prompts.** Consent prompts, y/N rendering, Ctrl-C behavior, TTY detection.
- **Console rendering on Windows.** Codepage 437/1252 output, table alignment, terminal width, whether error output looks alarming to a newcomer (Section 1.3).
- **Cross-Python reality.** The suite runs under one interpreter; Section 6 needs two installed.
- **Real hardware.** GPU presence, driver versions, CUDA toolkit variation, ComfyUI Portable's bundled CUDA.
- **Timing and feel.** Whether a no-op `--install` is fast enough to feel like a no-op.
- **Discovery against real disks.** ComfyUI Desktop layouts, multiple installs, network drives.
- **Long-run behavior.** Whether repeated runs stay idempotent over weeks as upstream indexes change.
